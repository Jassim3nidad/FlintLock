## Falsifiable predictions this revision makes — recorded before the device pass, not after

Two of this revision's fixes rest on a specific claim about hardware behavior that neither this session nor any prior one could actually observe — an argument from source code and documented platform behavior, not a measurement. Both are about to be tested for real. Recording, before that happens, exactly what a contradicting result would mean — so the next session (or this one, resumed) corrects the reasoning instead of quietly patching around whatever symptom shows up, or worse, reading a surprising result as confirming the existing fix because reversing course is more work than rationalizing.

1. **F5 — `.completeUnlessOpen` rests on the claim that MMKV's already-open mapping survives a background-then-lock cycle**, not merely that a *new* open is correctly denied while locked (that half is a documented OS guarantee, not a real risk, and isn't in question). **If device checklist §3 step 3 or step 4 produces a crash, a silently-dropped write, or file corruption, the correct response is not a narrower workaround around whatever specific operation triggered it.** It means the file-protection-class choice itself was wrong, and the real design question — MMKV's mmap-based access pattern against iOS Data Protection's revocation behavior across a lock — was reasoned about, never actually settled. That means revisiting `.completeUnlessOpen` vs. `.complete` from the start, not shipping a special case around the one failure mode a first device run happened to surface.
2. **F3 — the `E_UNKNOWN_ERROR` heuristic rests on an elimination argument derived from reading `react-native-keychain`'s Kotlin source**, not from observing a real device. **If device checklist §4's cancellation check (step 2) trips the invalidation branch — if an ordinary declined/cancelled prompt ever surfaces as `E_UNKNOWN_ERROR` instead of `E_CRYPTO_FAILED` — the heuristic is unusable as written and needs replacing with whatever the device actually reports, not widened or narrowed until that specific symptom stops appearing.** Curve-fitting the condition to make one observed failure go away is exactly how a heuristic like this quietly becomes wrong in a new, less-understood way instead of being genuinely fixed.

Both are stated so they can be falsified, not defended. A device result that contradicts either belongs in a revision note the same way every other correction in this document has — stated plainly, with what was wrong and why, not smoothed into a footnote on the existing fix.

A user copies a password, does something else, and the app visibly locks (the unlock screen reappears — a UI event that reads as "your secrets are now protected"). - **What was fixed — all three legs the corrected recommendation required, none optional, none deferred:**

It's state, not a one-shot event — deliberately, since a clear failing at lock time has no foreground UI to warn into; because verification only ever runs in the foreground handler, the warning is only ever raised at a moment when there *is* a foreground UI to show it in, closing the ordering gap the corrected recommendation flagged without needing to queue anything. `ClipboardWarningBanner` (new, mounted once at the unlocked app-shell root in `RootNavigator`) renders it as "Your clipboard may still contain a copied item" — generic by construction: `SessionClipboardGuard` is never given the copied value in the first place, so there is nothing for the banner to leak even by accident.

**F3 — Biometric hardware-invalidation and prompt-failure paths are unverified, and the test double structurally cannot exercise them** *(High — FIXED, committed `40ffccd`)*
- **Spec clause:** PROMPT.md §3 "Biometric unlock," point 5: "Any biometric enrollment change on the device invalidates the blob and forces password re-entry."
- **What was wrong:** `apps/mobile/src/biometric/nativeBiometricKeySource.ts`'s `unlock()` had no `try`/`catch` around `Keychain.getGenericPassword(...)` at all. Real `react-native-keychain`, for an item stored with `ACCESS_CONTROL.BIOMETRY_CURRENT_SET`, is well known to *throw* rather than return `false` when the enrolled biometric set changes — but the Jest double simulated this by clearing an in-memory `Map`, making `getGenericPassword` cleanly return `false`, never throw. `UnlockScreen.tsx`'s catch-all existed but was structurally unreachable by any test, because the mock could never throw into it.
- **The design call the fix needed, and how it was resolved:** a thrown error here isn't one thing — a declined prompt, a misread fingerprint, or a genuinely dead (invalidated) key all used to land in the same catch. Conflating them is itself a bug: treating every failure as "just retry" leaves a user stuck tapping a biometric-unlock button that can never work again after re-enrollment, with no explanation; treating every failure as "the key is dead" would incorrectly disable biometric unlock on an ordinary declined prompt. Distinguishing them needed react-native-keychain to actually surface enough signal to tell them apart — checked from the library's own source, not assumed, separately per platform since the two bridges are unrelated code:
  - **Android — traced end to end, a real if imprecise signal exists — stated honestly, not oversold.** `KeychainModule.kt`'s `getGenericPassword()` catches in three tiers. A prompt-level failure (declined, wrong finger, cancel, hardware error) is wrapped by `ResultHandlerInteractiveBiometric.onAuthenticationError()`/`onAuthenticationSucceeded()`'s own catch into `CryptoFailedException` *before* `KeychainModule` ever sees it → `promise.reject(Errors.E_CRYPTO_FAILED, ...)`. A genuine `android.security.keystore.KeyPermanentlyInvalidatedException` thrown during the actual decrypt call (inside `onAuthenticationSucceeded()`) is caught by that same handler's generic `catch (fail: Throwable)` — which does **not** wrap it into a more specific type — and falls through `KeychainModule`'s own final `catch (fail: Throwable) -> promise.reject(Errors.E_UNKNOWN_ERROR, fail)`. **`E_UNKNOWN_ERROR` is an elimination remainder, not a confirmation.** `isLikelyInvalidation()` treats it as "likely invalidation" because that's the best available signal by elimination — but by construction, the branch fires on *any* Keychain error this library's Android bridge doesn't recognize as a prompt-level failure or a keystore-access failure, not specifically and only on a confirmed key invalidation. Any other unrecognized native failure (a corrupted keystore entry, an OS-level bug, some other edge case this session didn't anticipate) would trip the same branch. **The asymmetry this creates, named plainly:** a false positive (some other unrecognized error mistaken for invalidation) costs the user a forced re-enrollment of a key that was actually still fine — an inconvenience, not a security regression, since the master password remains the only-ever fallback either way. A false negative (a real invalidation that somehow doesn't surface as `E_UNKNOWN_ERROR` on some Android version/OEM variant this session didn't test) restores exactly the pre-fix broken behavior: `unlock()` returns `null`, the button stays, and the user is back to tapping something that can never work with no explanation. Neither direction is confirmed on real hardware — both need a device check, not just the happy-path re-enrollment test (see the device checklist addition below and §5).
  - **iOS — no usable signal found, stated as a real limitation rather than guessed at.** `RNKeychainManager.m`'s `codeForError()` surfaces only the raw numeric `OSStatus` as a string (e.g. `"-25293"`), not a semantic code the way Android's bridge does. Which specific `OSStatus` value(s) a `.biometryCurrentSet`-invalidated item actually produces on a query, as opposed to a declined prompt or any other keychain failure, isn't confirmable from source alone — this session judged that guessing a magic number would be worse than not distinguishing at all. `unlock()` therefore never throws the new error on iOS; every iOS failure still returns `null`, identical to the pre-fix behavior. **F5 — iOS never set a file-protection class on vault storage** *(Medium — FIXED, committed `1d193ed`, `ea922ce`, `f42076a`)*
- PROMPT.md §2.6 names `NSFileProtectionComplete` specifically. It was absent entirely (only `isExcludedFromBackup` was set), and — unlike every other known gap in this codebase — undisclosed in `SECURITY.md`.
- **Deliberately implemented `.completeUnlessOpen`, not `.complete` — per instruction to choose, not default.** Reasoning, now also in a code comment on `hardenMmkvDirectory()` in `AppDelegate.swift` and in `SECURITY.md`:
  - `NSFileProtectionComplete` revokes access to a file's encryption key — for *already-open* descriptors, not just new ones — the instant the device locks. MMKV is mmap-backed: it maps its file into memory once and keeps that mapping open for the process's whole lifetime. Touching an `.complete`-protected mmap'd region while locked is documented Apple/MMKV-ecosystem behavior for a SIGBUS crash or an EPERM I/O failure. "Device locks while the app is merely backgrounded, not killed" is this app's *default* lock trigger (`lockOnBackground: true`), not an edge case — `.complete` would make an ordinary press-the-power-button action a crash risk.
  - `.completeUnlessOpen` (class C) lets an already-open descriptor keep working across a lock; only a *new* open is blocked until unlock. That matches MMKV's actual access pattern — the mapping opened at first access survives a background-and-lock cycle, while a cold launch that hasn't reached an unlock yet correctly fails to open the file, consistent with this app's fail-closed posture (and harmless, since the master password hasn't been entered in that scenario anyway).
  - The gap this leaves relative to `.complete` is narrow and is defense-in-depth on top of ciphertext either way — the vault's own AES-256-GCM encryption, not the OS file-protection class, is the actual confidentiality boundary. Still strictly stronger than the platform default (`.completeUntilFirstUserAuthentication`), which stays decrypted at rest after any single unlock since boot, indefinitely.
- **Implemented:** `apps/mobile/ios/Flintlock/AppDelegate.swift`'s `excludeMmkvDirectoryFromBackup()` renamed to `hardenMmkvDirectory()`, now also sets `resourceValues.fileProtection = .completeUnlessOpen`.
- **Disclosed:** added to `SECURITY.md`'s "Platform hardening" section (new bullet, "iOS file protection").
- **A second, deeper gap found while implementing this, and fixed in the same pass: iOS background "prewarming."** `.completeUnlessOpen` denies a *first* open while the device is locked — and iOS can launch this app in the background with **zero user interaction at all** (launch-time-optimization prewarming, silent push handling, background App Refresh), including while the device has never been unlocked since boot. Before this fix, `didFinishLaunchingWithOptions` called `factory.startReactNative()` **unconditionally**, rendering the full React tree regardless of launch reason — and `VaultSessionProvider`'s mount effect reads vault storage almost immediately. `react-native-mmkv`'s failure mode for a denied open is not guaranteed to be a catchable JS exception; MMKV's native core has a documented history of hard process aborts on iOS Data-Protection open failures, which no JS `try`/`catch` can intercept — a genuine OS-triggered crash-on-launch that manual testing (which always involves tapping the app icon) would never surface.
  - **Native guard: `AppDelegate.swift`'s `startReactNativeWhenDataIsAvailable()`** checks `UIApplication.isProtectedDataAvailable` before ever calling `factory.startReactNative()` — the risky `mmap()` attempt never happens during the locked-since-boot window at all, rather than being depended on to fail gracefully after the fact.
  - **A third gap, in the guard itself, found and fixed one revision later: no bound on the wait.** The first version of this guard, if data never became available, deferred indefinitely via `protectedDataDidBecomeAvailableNotification` with **no fallback UI at all** — the launch screen would sit frozen with no content and no way out, which isn't clearly better than the crash it replaced. A bounded timeout that starts React Native anyway after N seconds was considered and rejected: expiring that timeout while data is *still* unavailable would let `VaultSessionProvider` touch storage with the exact same unguaranteed-catchability risk the guard exists to remove — a bounded wait only bounds the time before hitting the risk, not the risk itself. **Fixed instead by showing a plain native "Unlock your device to continue" view** (`showWaitingForUnlockScreen`) immediately in place of starting React Native — touching nothing Data-Protection-gated — and waiting on the notification unboundedly, since it firing is the OS's own guarantee and the only condition under which this launch path is ever relevant to a real person. The observer closure runs `queue: .main` (confirmed by reading the call, not assumed), so `startReactNative()` is always dispatched on the main thread whenever the notification does fire.
  - **JS-side defense in depth (not the primary guard):** `apps/mobile/src/storage/native.ts` and `preferences/native.ts` both changed from an eagerly-created `export const vaultStorage = createMMKV(...)` (which attempted the native open the instant the module was first imported — unconditionally, on every launch including a prewarm) to a lazy `Proxy`-backed instance that defers `createMMKV()` until the first real property access, memoizes a thrown error rather than retrying immediately, and — for `preferencesStorage` specifically — lets `themePreference.ts` fall back to `'system'` on failure rather than propagate, since a wrong theme is cosmetic and this store was never meant to hold anything fail-closed-worthy. This catches whatever *is* catchable; it cannot help against a genuine native abort, which is why the native guard above is the one actually doing the load-bearing work.
  - **Device checklist extended:** `docs/CRYPTO.md`'s §3 gained a step for background prewarming, distinct from the existing manual cold-launch-while-locked case — a prewarm can't be triggered on demand from the app itself, so the checklist gives three approaches of decreasing reliability rather than a single definitive repro method.
  - **Unverified as of this writing**, same as the file-protection-class choice itself — whether `isProtectedDataAvailable` and the notification actually behave as documented on a real device, and whether the waiting screen actually appears (rather than, say, a blank window) if this path is ever hit while the app is genuinely visible, needs a physical device to confirm.
  - Committed as `1d193ed` (file protection), `ea922ce` (native guard + JS lazy init + doc follow-ups), and `f42076a` (bounding the guard's fallback).

**F17 — PROMPT.md §0.3's minimum-OS/hardware-keystore question was never actually settled — not a doc typo, a genuine open question, now answered** *(Medium — raised from Low; the README/`build.gradle` mismatch was a symptom, not the finding)*

- **StrongBox — a physically separate secure element, strictly stronger than a same-chip TEE — is unavailable below API 28 (Android 9) by hard OS limitation, not device variance.** No device in the app's declared 24–27 range can ever get it, confirmed by reading `react-native-keychain`'s own Android source: `CipherStorageBase.kt`'s `tryGenerateStrongBoxSecurityKey()` explicitly gates on `Build.VERSION.SDK_INT >= Build.VERSION_CODES.P` before attempting it at all.
- **But the app's code doesn't actually require StrongBox — traced the real enrollment path to confirm, not assumed:** `nativeBiometricKeySource.ts:38` requests `Keychain.SECURITY_LEVEL.SECURE_HARDWARE`, which `react-native-keychain`'s own `SecurityLevel.kt` defines as "stored on secure hardware (**Trusted Execution Environment or Secure [Element]**)" — TEE-or-better, not StrongBox-specifically. `CipherStorageBase.kt`'s `generateKeyAndStoreUnderAlias()` (the actual function `enroll()` runs through) tries StrongBox first when available, falls back to a regular TEE-capable Keystore key otherwise, and then — regardless of which path was taken — calls `keyInfo.isInsideSecureHardware` on the **real, just-generated key** and throws `CryptoFailedException("Cannot generate keys with required security guarantees")` if that check fails. This is a genuine, per-device, per-key, dynamically-enforced check, not a static claim the library makes about itself — confirmed by reading the actual `if (!validateKeySecurityLevel(...))` gate, not by trusting a comment.
- **Answering PROMPT.md §0.3 precisely, now:** the real floor is API 24 (required regardless, since `setInvalidatedByBiometricEnrollment(true)` — the mechanism PROMPT.md §3.5 names by requirement — doesn't exist before it). At that floor, biometric enrollment either succeeds with a real TEE-backed key (available since API 23, one version below the app's own floor) or fails closed with "Could not enable biometric unlock" — it never silently downgrades to a software-only key. **F28 — `generatePassphrase()`'s word/digit boundaries are unrecoverable from its own output when the drawn wordlist contains the separator character** *(Medium — new this session; see below for why this isn't the modulo-bias finding it was initially suspected to be)*
- **How this was found:** a `passwordGenerator.test.ts` failure appeared in one full-suite run and didn't reproduce in 31 immediate follow-up runs — initially treated as statistical noise from the file's own probabilistic uniformity check and reported that way. **That was premature and wrong, corrected on challenge**: "unlikely to fail by chance" is a claim about a *different* test in the same file, not a guarantee covering every assertion in it, and a rare wrong value is exactly the signature a real, low-probability-to-trigger bug produces. Re-chased with a 60-iteration scripted repro; reproduced on iteration 25 (roughly 1-in-25 to 1-in-30, consistent with the earlier 1-in-32 observation).
- **The exact failure:** `generatePassphrase › includeNumber appends a digit and adds log2(10) bits of entropy`, asserting `withNumber.value.split('-')` has length 5 for `wordCount: 4` (four words + one appended digit). Actual: length 6 — `["pamperer", "vaguely", "caliber", "yo", "yo", "5"]`.
- **Root cause, confirmed directly against the code, not inferred:** `randomInt()` (`packages/core/src/crypto/csprng.ts`) — the rejection-sampling primitive PROMPT.md §5.2 requires be bias-free — was re-read line by line specifically looking for an off-by-one in the accept condition (`if (value < exclusiveMax) return value;` — correct, standard half-open range) or a fall-through on retry exhaustion (there is no retry cap; the loop is unconditional `for (;;)`, so no exhaustion path exists to fall through). **No bug found in `randomInt()`.** The actual cause is one level up: the bundled EFF Large Wordlist genuinely contains four hyphenated compound words — confirmed by grepping the wordlist source directly: `"drop-down"`, `"felt-tip"`, `"t-shirt"`, `"yo-yo"` (and confirmed the bare word `"yo"` is *not* separately in the list, ruling out "two independent draws of the same word" as an alternate explanation). `generatePassphrase()` joins words with a caller-supplied `separator`, and every test — including the one that failed — uses `'-'`, the same character diceware convention and this codebase's own tests both default to. When the CSPRNG happens to draw `"yo-yo"`, the joined output contains an *extra* `-` that didn't come from the separator, so `value.split(separator)` — the exact operation the test uses to verify word count, and the exact operation any future consumer would reasonably use to reconstruct word boundaries — returns one array element per hyphen, not one per drawn word. Deterministic whenever a hyphenated word is drawn (~4/7776 per word, compounding to roughly 0.2–0.3% of passphrases at 4–6 words), not itself probabilistic in outcome — the *triggering* is what's rare, not the failure once triggered.
- **Why this is not a modulo-bias finding, despite matching the length-assertion trigger:** the entropy math, the selection distribution, and `randomInt()`'s own correctness are all unaffected — a passphrase containing `"yo-yo"` has exactly the same `wordCount * log2(7776)` entropy as any other, drawn with exactly the same uniform probability as any other word. PROMPT.md §5.2's "no modulo bias" requirement is about the *randomness*, which is sound here; this is a string-parsing/separator-collision defect in how the *output* is structured, a different category of bug. Recommending **Medium**, not High, on that basis — flagged explicitly as a divergence from the initial classification, since the severity this session was given depended on the mechanism being an RNG-correctness defect, and it isn't.
- **Current real-world exposure has two halves, not one — the first framing of this understated it by only counting the programmatic half, corrected on challenge:**
  - **Programmatic parsing (gated on a code caller existing):** `generatePassphrase()` has **zero callers anywhere in `apps/mobile/src`** — grepped directly, confirmed. `CredentialFormScreen.tsx` wires up `generatePassword()` (character mode) only. No screen, export path, or other consumer currently calls `.split(separator)` on a generated passphrase, so *this specific half* cannot currently produce a wrong result any real user sees.
  - **Human transcription (NOT gated on any code caller, and the more likely real-world path) — the half the original write-up missed.** The bug isn't confined to code that re-parses the output; it's an ambiguous artifact the moment a person *reads* it. `pamperer-vaguely-caliber-yo-yo` is visually indistinguishable from a genuine five-word passphrase — a user has no way to know, just by looking at it, that "yo-yo" was one draw rather than two. A user who reads this off the screen and types it into another device, writes it on paper, or dictates it to someone has no signal telling them where the real word boundaries are; miscounting a word here silently produces a *different, wrong* passphrase at the point of re-entry, not merely a rendering annoyance. This half activates the instant passphrase mode has *any* UI at all — it needs no `.split()` anywhere in the codebase to matter, and it is not mitigated by fixing the programmatic half alone (see the recommended fix below, corrected for exactly this reason).
- **A second, separate gap surfaced by checking that exposure, not previously flagged in any prior revision of this report:** PROMPT.md §5.2 requires "a passphrase mode (diceware-style wordlist bundled offline)" as part of the generator feature, by name, not as an optional extra. `generatePassphrase()` is fully implemented and tested in `packages/core`, but **no UI anywhere in `apps/mobile` exposes passphrase mode at all** — `CredentialFormScreen.tsx`'s generator is character-mode only. This is a spec-conformance gap in its own right, independent of the bug above — now tracked as its own entry in §6 (Spec drift), alongside F6's Trash UI, since it's the same shape: a feature PROMPT.md names by requirement that the code doesn't yet expose.
- **Recommended fix — corrected: the array return alone is not sufficient, only necessary.** Returning the drawn words as an array (`words: string[]`) alongside the joined `value` string fixes the *programmatic* half (no future code caller would ever need to reconstruct boundaries by splitting the display string) but does nothing for the *human-transcription* half — a person reading the screen still can't tell `words` from `value`, only code can. The fix that actually closes both halves has to happen at generation time, before wiring up any passphrase-mode UI: either exclude the four hyphenated entries (`drop-down`, `felt-tip`, `t-shirt`, `yo-yo`) from selection, or choose a separator guaranteed not to collide with any entry — confirmed cheap to satisfy, since these four hyphens are the *only* non-alphabetic characters anywhere in the 7776-word list (grepped for any entry containing something other than `a-z`; nothing else matched). Either change removes the ambiguity for a human reading the output, not just for code parsing it.

## 4. `.flbx` cross-version compatibility — answered empirically

**Question asked:** did anything check whether `.flbx` files produced before and after the monorepo extraction are still mutually readable? If the extraction changed serialization in any way, existing exports are the only backup users have.

**Short answer: yes, they are mutually readable, and this was verified empirically this session — not inferred from a code diff — in both directions, using a real artifact from the actual pre-extraction code.**

**Method:**
1. Diffed `flbxFormat.ts` across the two monorepo-restructuring commits (`b66e732`, `33009b4`) against the immediately-preceding pre-extraction commit. The on-disk binary layout, the `flbxAad()` construction, the header JSON shape, and every KDF/cipher call are byte-identical; the only changes are internal plumbing (`key.fill(0)` → `provider.disposeKey(key)`, synchronous → `await`-ed calls, import-path changes, a defensive `Buffer.from()` rewrap) — no behavioral or format change.
2. To go beyond a diff-based inference, checked out the real pre-extraction commit via `git worktree add` at the repo's own `pre-monorepo-native` tag (commit `112846b`, the last commit before the monorepo split began), ran `npm install` there, and used that checkout's **actual, unmodified `encodeFlbx()`** — with the real default 310,000-iteration PBKDF2 params, not a fast test stub — to produce a genuine `.flbx` artifact containing a credential and an attached TOTP entry.
3. Fed that real pre-extraction artifact into the **current** tree's `packages/core` `decodeFlbx()`. **Result: decrypted successfully, byte-for-byte correct payload, including the raw TOTP secret bytes** (asserted directly against the plaintext, not a generated code, to avoid timestamp-dependent flakiness).
4. Reversed it: encoded a second artifact with the **current** tree's `encodeFlbx()`, fed it into the **pre-extraction worktree's** `decodeFlbx()`. **Result: also decrypted successfully, byte-for-byte correct.**
5. Cleaned up: removed both throwaway test files from the current tree and the worktree, and removed the worktree (`git worktree remove`). `git status` is clean except for the changes already disclosed in §1 — no artifacts from this experiment were left behind or committed.

**Conclusion (original scope):** a `.flbx` file exported by the app before the monorepo extraction and one exported by the current code are mutually readable in both directions, for a credential + an attached TOTP entry with default PBKDF2 params.

**Extended, per instruction — full record-shape coverage, since exports are the only backup users have.** Repeated the same method (fresh `git worktree add` at `pre-monorepo-native`, real `npm install`, the actual unmodified pre-extraction `encodeFlbx()`) with a richer fixture in one direction (pre-extraction encode → current-tree decode):
- 2 tag records.
- 2 credential records — one exercising **all five `CustomFieldType` values** (`text`, `hidden`, `url`, `number`, `date`) on a single credential, plus two tag references, a two-entry `passwordHistory`, and `favorite: true`; the second a minimal credential with no tags/fields, to confirm the multi-record case isn't accidentally dependent on every record having the same shape.
- 1 TOTP entry attached to a credential.
- **1 standalone HOTP entry** (`credentialId: null`, `mode: 'hotp'`, `algorithm: 'SHA256'`, `digits: 8`, `counter: 42`) — the record type and mode combination not covered by the original narrower test.

Result: **decrypted by the current tree byte-for-byte and value-for-value identical to the source payload** — every custom-field type, both tags and their credential references, the password history, the favorite flag, and the HOTP entry's non-default algorithm/digit-count/counter all round-tripped correctly. Cleaned up identically to the original experiment (throwaway test files removed from both trees, worktree removed, `git status` shows nothing left behind).

**Conclusion, extended:** `.flbx` cross-version compatibility now has empirical coverage across every `VaultRecord` variant the schema defines (credential, TOTP, HOTP, tag) and every `CustomFieldType`, not just the narrower original case. Not separately re-tested in the reverse direction (current → pre-extraction) for this richer fixture, since the original bidirectional test already established the format itself doesn't differ between versions — the risk this extension was meant to rule out was a record-shape-specific serialization bug, which a one-direction test with full shape coverage is sufficient to catch.

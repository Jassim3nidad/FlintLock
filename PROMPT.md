## 1. What we're building

**Flintlock** is an offline-first password manager and 2FA authenticator. The whole product thesis is in one line: *a flintlock fires without external power — your vault works without a server.*

There is **no backend**. There is no account. There is no sync service. If a feature requires a server to work, it is out of scope.

**Target user:** privacy-conscious individuals who don't trust cloud password managers, and people in low-connectivity environments who need their credentials to work offline.

---

## 2. Non-negotiable security invariants

Treat these as hard constraints. If a feature request conflicts with one of them, stop and flag it instead of quietly compromising.

1. **The master password is never persisted** — not in storage, not in memory longer than key derivation requires, not in logs, not in crash reports.
2. **Plaintext secrets never touch disk.** Not in a temp file, not in an unencrypted cache, not in a debug log, not in async-storage.
3. **Vault data never leaves the device** except through an explicit, user-initiated export or Web Bridge transfer.
4. **No telemetry, no analytics, no crash reporting SDK, no ad SDK.** Zero third-party network calls.
5. **The app requests no network permission** other than what the Web Bridge needs on the local network. Document exactly what that is.
6. **No cloud backup.** Android: `android:allowBackup="false"`, `android:fullBackupContent` excluded. iOS: vault files marked `NSURLIsExcludedFromBackupKey` and stored with `NSFileProtectionComplete`.
7. **Screenshot / recents protection.** Android `FLAG_SECURE` on vault screens; iOS blur overlay on `applicationWillResignActive`.
8. **Fail closed.** Any decryption failure, tamper detection, or unexpected state locks the vault immediately — never degrades to a partial or plaintext view.

## 3. Cryptographic specification

Implement exactly this. Do not substitute or "improve" without asking.

### Key hierarchy (envelope encryption)

```
master password ──PBKDF2──► KEK (Key Encryption Key, 256-bit)
                                │
random 256-bit DEK ─────────────┴──AES-256-GCM wrap──► stored wrapped DEK blob
        │
        └── encrypts every vault record (per-record key, see below)
```

- **KDF:** PBKDF2-HMAC-SHA256, **310,000 iterations**, 32-byte cryptographically random salt, 32-byte output.
  - Store iteration count and salt in the vault header so the parameters can be raised later without breaking old vaults. Implement the upgrade path now, even if unused.
  - **Note for me:** PBKDF2 at 310k is the OWASP floor and matches the spec I gave you, but Argon2id (memory-hard) is meaningfully stronger against GPU cracking. If the platform has an audited Argon2id binding, propose it as `kdf: "argon2id"` in the header format with PBKDF2 retained for backward compatibility. Present this as a recommendation, don't just do it.
- **Cipher:** AES-256-GCM, **96-bit (12-byte) IV generated fresh from a CSPRNG for every single encryption operation**. Never reuse an IV under the same key. Never derive an IV from a counter that could reset.
- **AAD:** bind each record's ciphertext to its record ID and schema version via the GCM additional authenticated data, so records can't be swapped or replayed between vaults.
- **Auth tag:** 128-bit, always verified. A failed tag is a hard error, never a warning.
- **Randomness:** platform CSPRNG only (`SecRandomCopyBytes` / `java.security.SecureRandom` / native equivalent). Never `Math.random()`.

### Master password verification

Do **not** store a hash of the master password. Verification = attempt to unwrap the DEK and let the GCM auth tag succeed or fail. This gives verification for free with no extra attack surface.

### Biometric unlock

Biometrics unlock the DEK — they do **not** replace or weaken the password-derived key.

1. On enrollment (requires the master password), generate a hardware-backed key in Android Keystore / Secure Enclave with `setUserAuthenticationRequired(true)` and invalidation on biometric enrollment change.
2. Wrap a second copy of the DEK with that hardware key; store the wrapped blob.
3. Biometric success releases the hardware key → unwraps the DEK → vault opens.
4. The master password remains the only recovery path. Make this explicit in the UI at enrollment time.
5. Any biometric enrollment change on the device invalidates the blob and forces password re-entry.

### Memory hygiene

Zero out key material and decrypted plaintext buffers after use wherever the language allows it. Where it doesn't (JS strings are immutable), document the limitation honestly in `SECURITY.md` rather than pretending otherwise.

## 4. Data model

Design the schema; here's the shape I expect.

- **Credential** — id, title, username, password, URL(s), notes, tags[], custom fields[], favorite, created/updated/last-used timestamps, password history[].
- **TOTP entry** — can be attached to a credential *or* standalone. issuer, account, secret, algorithm (SHA1/256/512), digits (6/8), period (default 30), counter (for HOTP).
- **Tag** — id, name, color. Many-to-many with credentials.
- **Custom field** — key, value, type (`text` | `hidden` | `url` | `number` | `date`), per-credential. `hidden` fields are masked in the UI and excluded from search indexing.
- **Vault metadata** — format version, KDF params, salt, wrapped DEK blobs, created/modified timestamps, settings.

**Search must work without decrypting the entire vault into memory at once.** Propose an approach (encrypted search index vs. decrypt-on-demand with a bounded cache) and explain the tradeoff before implementing.

## 5. Features and acceptance criteria

### 5.1 Vault CRUD
Create, read, update, delete credentials. Soft-delete to a trash with a 30-day purge, hard-delete option, and a "delete permanently" confirmation that names the item.

### 5.2 Password generator
Length slider (8–128), toggles for upper/lower/digits/symbols, exclude-ambiguous option, and a passphrase mode (diceware-style wordlist bundled offline). Use the CSPRNG with rejection sampling — **no modulo bias**. Show entropy in bits, not a vague "strong/weak" bar alone.

### 5.3 Built-in 2FA authenticator
- RFC 6238 TOTP and RFC 4226 HOTP. Default SHA1/6 digits/30s; support SHA256, SHA512, 8 digits, custom periods.
- Add via QR scan, `otpauth://` URI paste, or manual base32 entry. Validate and normalize base32 input (strip spaces, handle missing padding).
- Live countdown ring, tap-to-copy, next-code preview.
- Handle clock drift: show a warning if device time is significantly off. Do not silently "fix" codes.
- *Optional, ask before building:* import from Google Authenticator's `otpauth-migration://` export (protobuf payload).

### 5.4 Tags and custom fields
Free-form tags with autocomplete, multi-tag filter (AND/OR), tag rename cascades. Custom fields per credential with the types listed above, reorderable.

### 5.5 Auto-lock and session expiry
- Configurable timer: immediate / 30s / 1m / 5m / 15m / 30m / never (with a warning on "never").
- Lock on app backgrounding (configurable), on device lock, and on the timer.
- Locking wipes the DEK and all decrypted state from memory.

### 5.6 Clipboard
Copy clears after **30 seconds**, with a visible countdown. On Android 13+, mark clipboard content sensitive (`EXTRA_IS_SENSITIVE`) so it's excluded from the clipboard preview. Clear the clipboard on app lock too, not just on the timer.

### 5.7 Export
Three formats, all user-initiated, all requiring master password re-entry immediately before export:

| Format | Encrypted | Notes |
|---|---|---|
| `.flbx` | **Yes** | Native format. Full fidelity: credentials, TOTP secrets, tags, custom fields, metadata. |
| CSV | **No** | Plaintext. Blocking warning dialog required. |
| KeePass XML | **No** | KeePass 2 XML schema for KeePassXC interop. Plaintext. Same warning. |

For the plaintext formats: an unmissable warning explaining the file is readable by anything on the device, plus a reminder to delete it after import elsewhere.

### 5.8 `.flbx` format
Design and document it in `docs/FLBX_FORMAT.md`. Requirements:
- Versioned magic header, plaintext KDF params + salt so any future version can open it.
- Its own independently derived key from the master password — do **not** reuse the vault's DEK.
- Whole-payload authentication; a truncated or tampered file fails cleanly with a clear error, never a partial import.
- Import is idempotent and offers merge vs. replace, with a preview of what will change before committing.

### 5.9 Web Bridge
Transfer credentials to a desktop browser over the local network. **This is the highest-risk feature in the app — treat it accordingly.**

Requirements:
- Local network only. No relay server, no cloud, no NAT traversal, ever.
- Ephemeral pairing: phone displays a QR code containing a one-time key and connection details; desktop scans/enters it.
- End-to-end encrypted channel keyed by the pairing secret. Assume the local network is hostile — a shared café WiFi must not yield plaintext.
- Session is time-boxed (suggest 2–5 minutes), single-use, and torn down on completion, on app background, or on timeout.
- Explicit per-transfer consent on the phone showing exactly what's being sent.
- Nothing persists on the desktop side beyond the browser tab's lifetime.

**Write the threat model in `docs/WEB_BRIDGE_THREAT_MODEL.md` and get my approval before implementing.** Cover: passive network sniffing, active MITM during pairing, malicious device on the same LAN, browser extension reading the page, and DNS/mDNS spoofing.

### 5.10 Dark mode
System-following, with manual override. True dark (not just inverted greys), verified for WCAG AA contrast. Design tokens, not hardcoded hex values.

### 5.11 Security dashboard (offline only)
Weak passwords, reused passwords, old passwords, credentials missing 2FA. All computed locally. **No HaveIBeenPwned lookup** unless I explicitly approve it later — it's a network call, and it contradicts invariant #4 as written.

## 7. Out of scope

Say no to these if they come up:

- Any server, account system, or sync service
- Password recovery, reset, or "forgot master password" — losing the master password means losing the vault, and the UI must say so plainly during onboarding
- Cloud backup or cross-device sync
- Browser extension (post-1.0 at the earliest)
- Any third-party SDK that phones home
- Custom cryptographic primitives
